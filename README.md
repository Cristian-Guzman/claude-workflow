# claude-workflow

A portable, self-improving slash-command workflow for [Claude Code](https://claude.com/claude-code).
Install it into any project, and it specializes itself to that codebase through use:
every completed ticket feeds patterns back into the project's own knowledge files,
so the commands get sharper the more you work.

## The pipeline

```
/clarify ──▶ /ticket ──▶ /verify ──▶ /qa ──▶ /pr ──▶ /ci-check ──▶ /learn
 investigate   implement    AC-check     QA guide   PR gen    CI watch     extract
 + blueprint   in phases    w/ evidence  or live    + commit  + merge      patterns
                                                                              │
                    ┌─────────────────────────────────────────────────────────┘
                    ▼
        .claude/codebase-patterns.md, testing-patterns.md, process-ledger.md
        (every future /ticket reads these — the system gets smarter per project)
```

Each command runs **once per ticket**, discretely — you pace the pipeline, nothing
auto-chains. State persists in `.claude/tickets/<ID>.md` so any session (or `/resume`)
can pick up where the last one stopped.

## Install

```bash
git clone <this-repo> && cd claude-workflow
./install.sh /path/to/your/project
```

Multi-repo workspace? Install once at the workspace root, then seed each repo:

```bash
./install.sh /path/to/workspace
./install.sh /path/to/workspace/repo-a --repo-only
./install.sh /path/to/workspace/repo-b --repo-only
```

**Updating:** `git pull` here, re-run `install.sh`. Core files refresh; anything the
project has made its own (patterns, settings, checklists) is never overwritten.

## Specializing to a new project — what actually matters

The commands read four project-owned files constantly. How fast the workflow gets
good in a new project is exactly how fast these get real content
(see [docs/specialization.md](docs/specialization.md) for the full guide):

1. **`repo-profiles/<repo>.yaml`** — base branch, CI command, dev server, test command.
   Generate with `/project-context`. Without it, commands ask you every time.
2. **`codebase-patterns.md`** — "how code is written here." Seed 2-3 entries manually
   (file placement, state management, error handling) or let `/learn` extract them
   after your first tickets. Most-read file in the system.
3. **`testing-patterns.md`** — test framework, where tests live, mock idioms.
4. **`ticket-checklist.md`** — what must be true before a PR (lint, tests, no debug
   logging, ...). The pr-branch-reviewer agent enforces this verbatim.

Everything else (`ui-fidelity-ledger.md`, `process-ledger.md`, debug session files)
is created automatically by the commands when first needed — don't seed it.

## Configuration points

- **Ticket system** — commands try MCP (Atlassian) first, then a `jira` CLI, then
  degrade gracefully to no-ticket mode (`/build` instead of `/ticket`). The repo
  profile is the single home for tracker config: set `tracker_system` and the
  numeric `jira_transition_*` ids in `repo-profiles/<repo>.yaml` (`_schema.yaml`
  documents how to look them up). `tracker_system: none` is a first-class mode.
- **Base branch** — recorded per repo in its repo-profile (`base_branch`). The
  included `guard-base-branch.sh` PreToolUse hook blocks accidental edits/commits
  on base branches and derives the protected-branch list from the profiles
  automatically — nothing to hardcode.
- **Single repo vs workspace** — the default layout is a multi-repo workspace
  (`.claude/` at the root that contains your repos). Installing into a single
  product repo also works: set `"env": {"WORKFLOW_LAYOUT": "single-repo"}` in
  `.claude/settings.json` so the branch guard treats the root as a product repo
  instead of a never-committed workflow root.
- **CI** — `/ci-check` uses `gh` (GitHub) by default; `/pr` detects the git host.
